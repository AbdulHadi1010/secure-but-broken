## D-005 — No C1+ arm; C2 has two moderator flavours (2026-10-03)

## D-006 — Moderator hallucination controls (2026-10-03)
Requirement from the researcher: the moderator must not hallucinate. Controls (to be built in P4, specified here so they are fixed in advance):
1. Temperature 0; same model and prompt hash for every repairer.
2. Grounding: moderator output is structured; every claim in `What failed` must cite an evidence item id. A checker rejects claims whose cited evidence does not contain the quoted text.
3. Leakage check (no YAML, no gold diff lines, no exact field values) — regenerate up to 2 times, then fall back to the deterministic template and log it.
4. Fallback rate and rejection reasons are reported in the paper as a metric.
5. Manual audit of a sample of moderator messages against their evidence (hallucination rate reported).

## D-011 — Gold hardening rules (2026-10-03)
Applied by `harness.gold.harden()` on top of D-010, nothing by hand:
1. Namespace `boutique` (no default namespace). No Pod Security Admission labels: `enforce` would block injected cases from deploying, and `warn` output could leak hints into feedback.
2. Pod `securityContext`: runAsUser/runAsGroup/fsGroup 10001, runAsNonRoot, seccompProfile RuntimeDefault. (Upstream already: no privilege escalation, drop ALL capabilities, read-only root FS, not privileged.)
3. `automountServiceAccountToken: false` on all ServiceAccounts and pods (no service calls the Kubernetes API).
4. ephemeral-storage requests 64Mi / limits 512Mi on every container (upstream already sets cpu/memory).
5. Upstream NetworkPolicy component v0.10.7 (default deny-all + per-service ingress allow-lists; egress open, as upstream), loadgenerator policy excluded.
6. `frontend-external` LoadBalancer Service removed; k6 reaches frontend in-cluster.
Result: Checkov 0 failed; remaining KICS/kube-score findings accepted with reasons in `app/gold/accepted-findings.md`.
Verified on kind (K8s 1.37.0): all 11 Deployments Available; journeys GET /, product, setCurrency, add to cart, view cart, checkout all HTTP 200.

## D-015 — Replace "easy/medium/hard" with cited classification + a-priori fix classes (2026-10-04)
Abdul challenged the difficulty labels in D-012: they were Claude's judgement with no source. Decision: the labels are dropped as a claim (build order kept as a work plan only). Each type is now described by (1) its Pod Security Standards profile (Baseline/Restricted) and NSA/CISA Kubernetes Hardening Guidance v1.2 section, both verified from pinned local copies (`docs/references/`), and (2) a fix class defined by us before any data: (a) remove/flip a setting, (b) choose an app-fitting value, (c) needs knowledge of the app's structure. Hypothesis H-FC (classes b, c break more often than a) is tested under RQ3. More classes may be added for stretch types. Supersedes the difficulty column of D-012.

## D-016 — Coupled fields: privileged forces allowPrivilegeEscalation (2026-10-04)
Verified on kind 1.37: the API server rejects `privileged: true` with `allowPrivilegeEscalation: false` ("cannot set allowPrivilegeEscalation to false and privileged to true"). The privileged injector therefore also removes the explicit `allowPrivilegeEscalation: false`. Each injector declares `target_rules` (L1 must clear them) and `coupled_rules` (findings caused by API-forced companion changes; must also clear, enforced through L2 "no findings beyond gold"). Case validation fails if any new finding is neither a target nor a declared coupled rule. Privileged targets: Checkov CKV_K8S_16, KICS dd29336b…, kube-score container-security-context-privileged; coupled: Checkov CKV_K8S_20, KICS 5572cc5e….

## D-018 — L7 security intent defined for all six types; L7 validated on every case (2026-10-04)
Intent per type is fixed in `policies/intent/README.md` and `harness/checks/intent.py` before any repair exists. Static part: Kyverno library ValidatingPolicies copied unchanged from kyverno/policies@ec478cb5 (Kyverno CLI v1.19.1, digest-pinned); gold passes all seven. Runtime part: /proc/1/status of the live process via an ephemeral debug container (CapBnd, NoNewPrivs, Uid), applied limits from the API, or a cross-namespace connection attempt. Trial showed a privileged non-root process has CapEff = 0 like gold, so "privileged" intent uses the bounding set (CapBnd ≠ full). Case validation gains V4: both the static and the runtime L7 check must flag the injected case. Injected capability for the capabilities type: SYS_ADMIN.

## D-019 — Class (b)/(c) injectors; scanners are blind to permissive NetworkPolicy (2026-10-04)
run-as-root is injected at POD level (runAsUser 0, runAsNonRoot false), because gold sets the non-root UID at pod level: a container-level injection would be fixed by deleting the override (class a), not by choosing a UID (class b). runAsNonRoot false is a coupled field (the kubelet refuses runAsNonRoot true with UID 0). missing-limits removes cpu/memory limits of the main container (requests and ephemeral-storage kept). netpol: trial `scripts/trials/2026-10-04_p2_netpol_injection_options.py` showed that a permissive policy (ingress from anywhere) is flagged by NONE of Checkov, KICS, kube-score; a missing policy is flagged only by kube-score (pod-networkpolicy). The netpol type therefore removes the service's policy and excludes the service from deny-all (coupled change; otherwise the service becomes unreachable and the case breaks). Variants use backend services that gold blocks from outside (cartservice, checkoutservice, productcatalogservice); frontend is excluded because gold intentionally admits all ingress to it. Consequence for RQ2: a repair that adds an allow-all policy satisfies every scanner and can only be caught by the L7 traffic probe.

## D-020 — Gate parameters, case variants and loop stop rules as implemented (2026-10-04)
L4 timeout 300 s (~7x slowest warm-cache ready time seen: 41 s baseline, 54 s case validation). 3 services per type (18 cases); netpol uses backends because gold admits all ingress to frontend. C1 stops once the scanner is clean (that is prior work's success criterion); C2 stops on SAFE_FIX; all conditions max 5 iterations except C0 (1). Unparsable replies get the same fixed format reminder in every condition. CLAUDE.md has no label for L1 pass + L2 fail; implemented as NOT_FIXED with l2=false recorded, pending Abdul's confirmation before the pilot. Written into protocol.md.

## D-021 — L7 probe profile and V4 rule corrected after class b/c validation (2026-10-04)
(1) The /proc probe used `kubectl debug --profile=restricted`, which forces runAsNonRoot=true: in run-as-root pods the debug container could not start and the probe returned no data. The run-as-root cases therefore "passed" V4 because the probe failed, not because it saw UID 0, and every correct repair would also have failed L7. Probe now uses `--profile=general`. (2) V4 required the static Kyverno check to flag the case, but netpol has no static policy by design (intent = traffic), so valid netpol cases (runtime probe: OPEN) were marked invalid. V4 now requires: runtime probe produced data AND shows the violation, and the static check flags it unless the type has no static policy. All 18 cases are re-validated with the corrected instrument; earlier validation.json files are superseded (kept in git history).

## D-027 — P5 scaling: identical VM fleet + SQS queue instead of Batch/Spot/Step Functions (2026-10-04)
Deviation from CLAUDE.md §6, approved by Abdul ("spot may cause issues with our test"). Workers = on-demand c6i.2xlarge launched from an AMI of the validated measurement VM (same OS, tools, warm image caches). Jobs = one SQS message per chain (case × model × condition × repeat); visibility 2 h; after 2 failed receives a job goes to a dead-letter queue (never silently dropped). Each worker first qualifies by running gold through the full pipeline (must be SAFE_FIX inside the active L6 band) and refuses work otherwise; one chain at a time per worker; workers stop themselves after 15 min idle. Each batch has a manifest in S3 (batches/<label>/manifest.json) and a done marker per chain, so completeness is checkable (`harness completeness <batch>`). Workload estimate for the full experiment: ~1,100 attempts × ~5 min ≈ 90 VM-hours (~1 day on 4 VMs, ~USD 31 compute).

## D-028 — C2 evidence and grounding fixes after the P4 loop check (2026-10-04, before the pilot)
Loop check (exploratory) on netpol-cartservice / DeepSeek: C1 stopped at iteration 1 (scanner-clean, BREAKING) as designed; C2-template ended NOT_FIXED and C2-LLM INVALID_OUTPUT after 5 iterations. Inspection found two instrument flaws, fixed generically (not tailored to the case): (1) the grounding check accepted only single citations "[E2]"; the moderator wrote grouped citations "[E1, E2, E3]", so 3 of 4 moderator messages were rejected and replaced by the template (C2-LLM silently became C2-template). Grouped citations now count. (2) Runtime evidence held logs only for non-Ready pods; here all pods were Ready and the cause (cartservice could not reach its dependency) was only in logs of healthy pods. Evidence now adds recent error-like log lines from every pod when L5/L6 fail. Evidence wording also made explicit ("did not return HTTP 200", "must be at most 14.5 ms") after the moderator misread "limit" as a minimum. Leakage check unchanged (conservative: a port number from the gold diff in an LLM message still triggers a regeneration).

## D-029 — A reply that omits objects is judged by the gates, not INVALID_OUTPUT (2026-10-04)

## D-030 — L7 also requires "no regression" of any other security control (F13) (2026-10-06)
Abdul: a repair that weakens other security controls is not acceptable in production, so the study must treat it as deceptive even when the target service stays protected. Defined BEFORE the pilot; L7 pass = target intent (unchanged, D-018) AND no regression:
(1) all seven Kyverno library policies pass for every workload other than the target (the target is judged by its own intent);
(2) no NetworkPolicy present in the case given to the repairer is deleted, has its pod selection changed (widening to all pods is allowed) or loses policy types;
(3) at runtime, every service gold shields from outside traffic (derived from gold's own policies: 10 backends, not the frontend) still refuses a connection from another namespace.
Recorded per attempt under intent.regression; `target_pass` kept separately so the analysis can report both. Known-answer test added: gold with the deny-all policy deleted, as the repair of netpol-cartservice, must be DECEPTIVE_FIX.

## D-036 — How the frozen analysis plan was implemented (2026-10-16, before looking at P7 results)
Written while the P7 chain table was building, before any P7 verdict was read; no change to the plan's tests or outcomes. (1) "Fisher exact where expected counts < 5" for r x c tables (RQ3) = Monte Carlo permutation test of independence (chi-square statistic, margins fixed, 100,000 resamples, seed 20261016), `analysis/stats.py::rxc_exact`, because scipy's exact Fisher is 2x2 only. (2) H-FC uses all chains of the wording pooled over models AND conditions, final verdicts, among scanner-clean chains (RQ1 definition). (3) scanner-clean is derived from the verdict (SAFE/BREAKING/DECEPTIVE/BREAKING_AND_DECEPTIVE all require L1 and L2). (4) The risk-difference CI is Newcombe's (unpaired) as pre-registered; it ignores the pairing, so it can include 0 while the paired McNemar test rejects — reported as is. (5) The mixed-effects regression (sensitivity) is not yet run.

## D-037 — Fitting method for the mixed-effects sensitivity analysis (2026-10-16)
The pre-registered robustness model (SAFE_FIX ~ condition + model + type + wording, random intercept per case) cannot be fitted by maximum likelihood here: several types have 100% SAFE_FIX (complete separation). Fitted instead with statsmodels BinomialBayesMixedGLM (variational Bayes, default weak priors), references C1 / kimi-k3 / privileged / W0; analysis/p7_regression.py. Variational Bayes can understate uncertainty, so the regression stays a sensitivity check, never the primary test. Result agrees with the primary tests (C2-LLM and C2-template above C1, C0 not different from C1, DeepSeek lowest, NetworkPolicy lowest).
