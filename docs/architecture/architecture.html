Secure but Broken? Deployment-validated evaluation of LLM security repairs for Kubernetes

An LLM is asked to fix one injected security misconfiguration in a Kubernetes app. Prior work stops when the scanner goes quiet. We deploy every repair on a fresh cluster, drive real traffic through it, and check that the security intent is actually met. Then we test whether feeding runtime failures back to the LLM produces fixes that are both secure and working.

For discussion

Known gaps and open questions

What a reviewer could challenge today, and where each item is handled. Feedback on anything missing is welcome.

OPEN

Repairer prompt wording

One fixed, pre-registered prompt for all models and conditions, never tuned on test cases. Undecided: does it say "keep the application working"? The other wording becomes a sensitivity check on a subset.

OPEN

Newest frontier models unavailable

Claude Sonnet 5.5 and GPT-5.5 are blocked on this account. The study uses Sonnet 4.6, GPT-OSS 120B and DeepSeek V3.2, and will say so.

RESOLVED

NetworkPolicy enforcement in kind

Tested: kindnet blocks a connection the policy forbids and allows the permitted caller (D-017). Also found: no scanner flags a policy that admits all ingress, so only the runtime probe can catch that deceptive fix (D-019).

RESOLVED

Runtime probes on minimal images

An ephemeral debug container reads /proc of the app process. Found on the way: a privileged container running as non-root shows zero effective capabilities, like the hardened app; only the bounding set gives it away (D-018).

RESOLVED

Coupled fields

Each injector declares its target and coupled scanner rules; case validation fails on any unexpected finding (D-016).

P4

Moderator grounding and leakage check

Every moderator claim must cite evidence; messages with YAML or gold lines are rejected. Hallucination and fallback rates are reported.

P5

kind inside AWS Batch

Needs privileged worker containers on EC2 compute (not Fargate), plus image caching. The working band must be re-measured on the Batch instance type before comparing.

P6

Drift and sample size

Baseline p95 rose run over run (136→199 ms). Plan: periodic gold control runs during experiments, and a sample-size check from pilot variance before freezing the protocol.

P7–P9

Verdict audit

A manual audit of a random sample of verdicts, with a second rater on a subset, to show the automated checks agree with human judgement.

Every step is recorded in the project journal; decisions and deviations are numbered (D-001 onward). Sources for the security classification: Kubernetes Pod Security Standards and the NSA/CISA Kubernetes Hardening Guidance v1.2 (Aug 2022), pinned locally with SHA-256 hashes.
